1. Big Picture

This app is a local-first personal finance tracker built with Flutter. It stores data on the device using Hive, shows that data in a cyberpunk-styled UI, and organizes the code into a simple layered architecture.

Core Purpose

Track accounts, record income and expenses, view statistics, and inspect exchange rates.

Main Layers

UI Screens → FinanceService → HiveService → Hive boxes → local device storage. 

Presentation Layer
  lib/screen/*.dart

Business Logic Layer
  lib/services/finance_service.dart

Persistence Layer
  lib/services/hive_service.dart
  lib/models/*.dart
  Hive local database
Teacher note: This is not a heavy enterprise architecture. It is a practical small-app architecture. That is good. The code is understandable because there are not too many layers.

2. Startup Flow

The app begins in lib/main.dart. This file does three important jobs:

  • initializes Flutter binding
  • starts the app widget tree
  • waits for Hive initialization before showing the dashboard
void main() {
  WidgetsFlutterBinding.ensureInitialized();
  runApp(const FinanceTrackerApp());
}

The interesting part is the FutureBuilder. Instead of assuming storage is ready, the app waits for HiveService.initialize(). That avoids the old class of bug where a Hive box is used before it has been opened.

Student takeaway: If your app depends on a database, do not render the real UI before the database is ready.

3. Data Models

The project has two main domain objects.

3.1 AccountModel

lib/models/account_model.dart

class AccountModel extends HiveObject {
  String id;
  String name;
  double balance;
}

This is the simplest representation of an account. It has:

  • id: unique identity for storage and linking
  • name: human-readable label like “Daily Card” or “Savings Vault”
  • balance: current balance stored directly on the account

3.2 TransactionModel

lib/models/transaction_model.dart

enum TransactionType {
  income,
  expense,
}

class TransactionModel extends HiveObject {
  String id;
  String title;
  double amount;
  TransactionType type;
  String category;
  DateTime date;
  String? photoPath;
  String? accountId;
}

The transaction model is richer because transactions are the real activity of the app.

  • title: description like “Groceries” or “Monthly Salary”
  • amount: money value
  • type: income or expense
  • category: grouping for charts and filtering
  • date: when it happened
  • photoPath: optional receipt image path
  • accountId: optional link to an account
Teacher note: Notice that TransactionModel stores accountId, not an entire account object. That is a good local-database design because it avoids nested duplication.

4. Persistence Layer

lib/services/hive_service.dart

HiveService is the single place that knows how to boot the local database.

4.1 What It Opens

  • transactions box
  • accounts box
  • settings box

4.2 Why This File Matters

Without this file, every screen or service might try to initialize Hive on its own. That would create duplicated setup code and more opportunities for errors. 

static Future<void> initialize() async {
  await Hive.initFlutter();
  register adapters;
  open boxes;
}

4.3 The Hidden Safety Rule

The getters like transactionsBox and accountsBox call _assertInitialized(). That means the app fails early and clearly if somebody tries to use Hive too soon.

5. Business Logic Layer

lib/services/finance_service.dart

This is the most important non-UI file in the project. If the screens are the face of the app, FinanceService is the brain.

5.1 Responsibilities

  • read transactions and accounts
  • calculate totals
  • track the selected overview account
  • seed preview/demo data
  • keep account balances in sync when transactions change

5.2 Why This Is Good

Screens do not directly manipulate Hive everywhere. Instead, they call methods like:

  • addAccount()
  • deleteAccount()
  • addTransaction()
  • updateTransaction()
  • deleteTransaction()

5.3 Important Logic: Account Balances

One of the smartest parts of this app is that account balances are automatically updated when transactions change. 

addTransaction(transaction)
  save transaction
  apply transaction to linked account

deleteTransaction(transaction)
  revert transaction from linked account
  delete transaction

This means the account balance is treated as a live derived value that is also stored for fast display.

5.4 Important Logic: Preview Data

The app seeds demo content such as Daily Card and Savings Vault. That is useful during design work because dashboards and charts look better with realistic data.

Student takeaway: When you read a screen file and see totals or balances, ask: “Did the screen calculate this, or did the service calculate this?” In this app, the service handles most of it.

6. Screen Architecture

The screens are in lib/screen/. Each screen has a focused role.

DashboardScreen

Home page, overview, summary cards, chart widgets, navigation shell.

AccountsScreen

Manage account list, open account detail, show account settings sheet.

TransactionListScreen

Filter and browse transactions.

TransactionFormScreen

Create or edit a transaction.

StatisticsScreen

Monthly and yearly charts with filters.

ExchangeRateScreen

Rates dashboard plus currency converter.

7. Dashboard Walkthrough

lib/screen/dashboard_screen.dart

This file is the largest screen because it acts like a mini command center for the app.

7.1 What Happens in initState

initState() {
  _seedPreviewData();
}

The dashboard ensures the app has demo data if needed. That means the first experience is not empty.

7.2 What It Reads

  • accounts
  • selected overview account
  • income
  • expenses
  • recent transactions
  • expense category breakdown
  • account-specific chart data

7.3 Why This File Is Big

It is not just a screen. It also contains many private helper widgets and data-shaping functions:

  • bottom navigation widgets
  • cash-flow cards
  • recent transaction panels
  • expense category legend items
  • chart helpers for balance history
Teacher note: This is a good example of a Flutter pattern where one screen file contains many private classes starting with an underscore. That keeps them local to the screen and prevents the rest of the project from depending on tiny implementation details.

7.4 UI Hierarchy on the Home Page

Dashboard
  AppBar
  Hero balance card
    Month label
    mode badge
    total balance
    account selector
  Cash flow / recent transactions card
  Focused account chart or expense chart
  Bottom navigation shell
  Floating quick-add button

7.5 Key Architectural Idea

The dashboard does not own the truth of the data. It asks FinanceService for the truth, then transforms that truth into visual sections.

8. Transactions Flow

8.1 Transaction List

lib/screen/transaction_list_screen.dart

This screen is intentionally straightforward.

  • it fetches all transactions from FinanceService
  • it filters by type if needed
  • it sorts by date direction
  • it opens detail or form screens when the user interacts

8.2 Transaction Form

lib/screen/transaction_form_screen.dart

This screen shows strong practical form logic:

  • supports create and edit mode
  • changes default category when type switches
  • supports a custom “Other” category field
  • lets the user attach a receipt photo
  • lets the user link the transaction to an account
saveTransaction():
  validate form
  build TransactionModel
  if editing:
    FinanceService.updateTransaction(...)
  else:
    FinanceService.addTransaction(...)
  close screen

8.3 Why This Matters Architecturally

The form screen creates data objects, but it still does not handle balance math itself. That logic stays inside FinanceService.

9. Statistics Flow

lib/screen/statistics_screen.dart

This screen converts raw transaction history into chart-friendly structures.

9.1 Inputs

  • selected account scope
  • selected series filter
  • transactions for that selection

9.2 Outputs

  • summary cards for income, expenses, balance
  • monthly overview chart
  • yearly totals chart

9.3 Important Design Choice

The statistics screen starts from the current overview account, but still allows the user to change the scope. This creates a nice connection between the dashboard and analytics pages.

Student takeaway: A chart screen usually needs a “data preparation layer.” Here, helper methods like _buildMonthlyStats() and _buildYearlyStats() perform that transformation.

10. Exchange Rates Flow

lib/screen/exchange_rate_screen.dart

This screen is the only part of the app that talks to the network. It fetches data from the Frankfurter API.

10.1 Responsibilities

  • load EUR-based USD and GBP history
  • draw a 30-day line chart
  • provide a converter with amount, from-currency, and to-currency
  • compute derived pair rates such as USD → GBP or GBP → EUR

10.2 Architectural Note

This screen currently keeps its API logic inside the screen state class rather than moving it into a separate service. For a small app, that is acceptable. For a larger app, you might extract an ExchangeRateService.

11. End-to-End Data Flow

Here are three important user flows explained from screen to storage.

11.1 Add Transaction

User opens TransactionFormScreen
  ↓
User fills fields
  ↓
TransactionModel is created
  ↓
FinanceService.addTransaction(...)
  ↓
Transaction saved to Hive
  ↓
Linked account balance is updated
  ↓
Dashboard and lists refresh on navigation return

11.2 Delete Account

User confirms delete
  ↓
FinanceService.deleteAccount(account)
  ↓
All linked transactions are unassigned
  ↓
Account is removed from Hive
  ↓
Selected overview account is repaired if necessary

11.3 Change Overview Account

User selects account on dashboard
  ↓
FinanceService.setSelectedAccountId(...)
  ↓
Selected account id is saved in settings box
  ↓
Dashboard and statistics use the new focused account

12. Design Patterns Used

12.1 Service Layer Pattern

FinanceService centralizes business rules.

12.2 Repository-Like Access

The service reads and writes data for screens, even though it is not formally named a repository.

12.3 Local Widget Composition

Large screens define many private widget classes in the same file to keep the screen modular without over-fragmenting the project.

12.4 Stateful UI with Local State

Most screen-level state is stored directly in State<...> classes instead of using Riverpod, Bloc, or Provider. That keeps the app approachable for learning.

13. Improvement Ideas

The app is already solid, but here are some realistic next steps.

  • extract an ExchangeRateService for network logic
  • split very large screen files like dashboard_screen.dart into smaller parts
  • add stronger automated tests around account-balance synchronization
  • introduce a typed settings wrapper instead of using the raw settings box directly
  • consider a state-management package if the app grows much larger
Teacher note: Do not rush to add architecture for architecture’s sake. The current structure is good for a project of this size. Improvements should follow real complexity.
